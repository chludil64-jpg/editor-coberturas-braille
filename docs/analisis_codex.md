# Análisis de Editor Braille

Revisión estática del repositorio para una PC escolar y una persona usuaria. Prioridad según impacto probable en ese uso; las líneas son aproximadas. Referencia de accesibilidad: [WCAG 2.2, nivel AA](https://www.w3.org/TR/WCAG22/). No se hizo una prueba práctica con NVDA, ampliador ni impresora.

## A. Interfaz, uso y accesibilidad

- **Alta — Edición de vértices y trazos sin alternativa completa de teclado.** `web/js/lienzo.js:481-536`, `web/index.html:168-170,217-236`. El lienzo permite seleccionar, mover y trazar un lazo con teclado, y hay una lista textual y entrada de coordenadas; pero agregar un vértice, cortar una línea y algunas acciones sobre manijas dependen del puntero. Para un docente que usa lector de pantalla, una corrección fina del mapa puede quedar bloqueada (WCAG 2.1.1). **Propuesta:** llevar esas operaciones a la lista de elementos con acciones enfocables y edición numérica de vértices, tramo y transformación; anunciar el resultado y devolver el foco al elemento.
- **Alta — Rendimiento y memoria al abrir material grande.** `web/js/proyecto.js:54-65,158-186`, `web/js/lienzo.js:41-49,96-127,553-555`, `web/js/imagen.js:3,9-15`. Cada cambio puede serializar el documento entero para deshacer (hasta 150 copias); el dibujo redimensiona y repinta todo el canvas, y las miniaturas SVG se generan sin límite. Un PDF incluido en el proyecto, una imagen grande o un mapa de muchos trazos pueden congelar la PC y hacer perder el trabajo. **Propuesta:** límites visibles antes de importar, historial por cambios sin duplicar PDF e imágenes, repintado agrupado con `requestAnimationFrame` y canvas de fondo separado; mostrar progreso y permitir cancelar importaciones largas.
- **Media — Cinta y flujo docente dispersos.** `web/js/cinta.js:19-50,150-177`, `web/index.html:73-104,263-297`. “Archivo” mezcla abrir `.ibe` con exportaciones; “Formato” solo ofrece página nueva; “Impresora” y “Inicio” repiten imprimir. La ruta habitual abrir PDF → elegir textos → revisar avisos → PDF 1:1 → imprimir exige saltar entre paneles y pestañas. **Propuesta:** ubicar acciones según tarea, mantener una sola acción principal de impresión y ofrecer una secuencia visible “Preparar, revisar, probar, imprimir” con página activa y estado de guardado.
- **Media — Información para baja visión demasiado pequeña y truncada.** `web/tema.css:94-108,140-151`, `web/js/lienzo.js:52-79`, `web/estilos.css:218-222`. La cinta usa texto de 0,7–0,8 rem, las reglas del lienzo 10 px y la barra de estado recorta mensajes; a 200 % de zoom la lectura y localización de avisos se dificultan. **Propuesta:** elevar tamaños mínimos, permitir ampliar texto/reglas independientemente del zoom del papel, envolver rótulos y mensajes, y comprobar reflujo a 320 CSS px/200 % (WCAG 1.4.4 y 1.4.10). Mantener los contrastes actuales como base y medir estados de selección, bordes y foco en ambos temas (1.4.3 y 1.4.11).
- **Media — Mensajes simultáneos y avisos poco estables.** `web/index.html:172,263-269`, `web/js/proyecto.js:109-115`, `web/js/principal.js:102-138,173-181`. `anuncio` usa `aria-live="assertive"` con `role="status"`, mientras el estado del lienzo y varios diálogos tienen otras regiones vivas: un mismo cambio puede interrumpir o repetirse en el lector. El estado visible se trunca. **Propuesta:** una región `polite` para rutina, `alert` solo para fallas que exijan actuar, mensajes persistentes y enfocables para impresión/errores, y pruebas con NVDA + Edge del orden de anuncios (WCAG 4.1.3).
- **Baja — Hay bases accesibles, pero falta verificación integral.** `web/index.html:17-19,168-170`, `web/js/cinta.js:125-144`, `web/estilos.css:224-226`, `web/tema.css:49`. Existen enlaces para saltar, foco visible, pestañas con flechas y alternativa textual al canvas; las transiciones respetan movimiento reducido. **Propuesta:** recorrer el flujo completo solo con teclado y NVDA, verificar orden y retorno de foco en diálogos, foco no tapado (2.4.11), tamaño/espaciado de objetivos (2.5.8), contrastes AA y reflujo. Registrar los fallos observados antes de declarar conformidad WCAG.

## B. Seguridad

- **Alta — La API local permite consumo excesivo de CPU y memoria.** `app.py:29,37-45,121-129,148-157,191-224`, `motor/pdf_io.py:29-65,169-175`, `motor/index_v4.py:124-154`. El límite de 80 MiB cubre bytes de petición, pero no páginas del PDF, cantidad de puntos, dimensiones de salida ni trabajo de renderizado/exportación; `ThreadingHTTPServer` suma peticiones concurrentes. Un archivo malicioso o una pestaña local comprometida pueden congelar la PC durante una clase. **Propuesta:** límites por tipo (páginas, objetos, puntos, píxeles, dimensiones A4, concurrencia y tiempo), validar números finitos y rangos antes de asignar memoria; devolver 413/422 legibles. Mantener el límite de bytes, pero tratarlo como una defensa parcial.
- **Media — Parámetros RAW de impresora y destino de red demasiado confiados.** `app.py:62-89,237-269`, `motor/perfil.py:51-79,128-133`, `motor/index_v4.py:49-56,191-198`, `motor/impresion.py:58-90`. El nombre de impresora Windows se compara con la lista instalada, lo que reduce inyección por ese campo. En cambio, el perfil aceptado por la API puede aportar valores al encabezado ESC de `.ibe`/`.prn`, y `destino.ip` admite cualquier host alcanzable. En una app local de un usuario, el riesgo principal es una salida RAW incorrecta, gasto de material o conexión a otro equipo de la red; no hay ejecución de comandos del sistema por el nombre. **Propuesta:** esquema estricto para perfil y puntos, solo parámetros numéricos y enumeraciones admitidas por la Index, sin controles ASCII; validar IP literal y puerto 1–65535, y permitir destinos de impresión configurados o pedir confirmación que muestre la dirección final.
- **Media — PDF, SVG, imágenes y proyectos no confiables.** `app.py:191-196`, `motor/pdf_io.py:13-34,63-66`, `web/js/svg_importar.js:33-55,103-114`, `web/js/imagen.js:3-15`, `web/js/proyecto.js:191-206`. PyMuPDF procesa PDF de terceros y el navegador decodifica imágenes; el SVG se analiza como XML y se convierte a geometría, sin insertarlo como HTML ni ejecutar sus `script`, por lo que **no se observa una vía directa de XSS/XXE** en ese flujo. Sí pueden agotar recursos un PDF comprimido, una imagen de dimensiones enormes o un SVG con miles de nodos/curvas; un proyecto JSON puede traer `src` de referencia arbitrario. **Propuesta:** límites de tamaño y complejidad antes y después del parseo, cancelar tareas largas, aceptar solo `data:image/png`/JPEG para referencias guardadas y fijar una versión mínima probada de PyMuPDF con revisión periódica de avisos de seguridad.
- **Baja — CSRF y DNS rebinding: controles útiles, con un margen de endurecimiento.** `app.py:99-101,136-161,183-189,285-289`, `web/js/proyecto.js:118-128`. El servidor se liga a `127.0.0.1` (no a `0.0.0.0`), exige `Host` local y la cabecera `X-Editor-Braille: 1` para POST/PUT; una web ajena no puede agregarla mediante un formulario simple y un `fetch` con esa cabecera requiere preflight CORS, que el servidor no habilita. El riesgo de órdenes remotas casuales es bajo. `GET` expone perfil, nombres de impresoras y PDFs cargados si otra web lograra leer el origen local. **Propuesta:** comprobar también `Origin`/`Sec-Fetch-Site` en operaciones sensibles y usar un token aleatorio por sesión; mantener el control de `Host` y no abrir CORS.
- **Baja — Rutas de archivos: alcance acotado, symlinks como excepción.** `app.py:167-177,197-199,246-251`, `web/js/proyecto.js:177-199`. El servidor no recibe rutas para abrir/guardar proyectos: el navegador usa selector y descarga; el perfil y la copia RAW tienen rutas fijas. El estático normaliza y exige prefijo `web/`, por lo que `../` común no sale de la carpeta. Si alguien con acceso local coloca un enlace simbólico dentro de `web/`, `isfile` seguiría el enlace y podría exponer el archivo apuntado. **Propuesta:** resolver `realpath` y comprobar pertenencia a `WEB` antes de abrir; evitar servir archivos agregados por usuarios. Riesgo bajo en una PC de una persona sin acceso de otros al repositorio.
- **Baja — Service worker y caché.** `web/sw.js:3-21`, `web/js/principal.js:471`. No cachea `/api/`, lo que evita guardar PDFs y respuestas sensibles; usa red primero. Si el servidor está apagado, puede servir una interfaz vieja sin backend, y el caché conserva recursos de versiones anteriores hasta activación. **Propuesta:** versionar la caché con cada versión, mostrar “servidor desconectado” al fallar la API y limpiar cachés viejas; verificar que nunca se cacheen proyectos ni archivos del usuario.
- **Baja — Dependencias.** `LEEME.md` (Requisitos), `motor/pdf_io.py:6`, `web/index.html:13-14`. La app evita paquetes JS remotos y usa Python stdlib más PyMuPDF, pero la documentación instala PyMuPDF sin versión fijada. **Propuesta:** registrar versión mínima y versión probada, mantener actualizaciones de seguridad de Python, navegador y PyMuPDF, y revisar el paquete antes de distribuirlo en PCs escolares. El riesgo depende de que se abran archivos de origen no confiable.
